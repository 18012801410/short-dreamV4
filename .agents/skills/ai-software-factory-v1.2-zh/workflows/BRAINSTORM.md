# 头脑风暴工作流（Brainstorming Workflow）

通过结构化的提问，把一个粗略的想法变成经人类批准的意图——先于任何规格或代码。

只要想法是新的、或改动是架构级的，就必须在任何规格生成（`workflows/SPEC_GENERATION.md`）之前运行本工作流。它唯一的产出是落成文字、且经人类批准的意图。

<HARD-GATE>
在人类批准第 5 步呈现的设计之前，不得编写产品代码、不得搭建项目脚手架、
不得运行任何实现类工作流。流程的繁简随任务大小缩放，但批准这道闸门永远存在。
</HARD-GATE>

## 第 1 步 — 对请求分类

在提出第一个问题之前，先对请求分类，并把分类结果说出来，让人类可以推翻：

- **技术验证（Spike）**——一个可行性问题（"能不能……"、"可不可能……"），产出是一个答案，而不是要保留的代码。用 2-3 句话呈现问题和验证计划，得到点头后，用尽可能便宜的方式探个究竟，然后报告结论建议。凡是造出来的东西都标注为"用完即弃"。不写简报，不写规格。
- **有界改动（Bounded）**——对仓库中已有代码的范围清晰的改动：加个开关、一个小端点、单文件修复。把关键的澄清问题问掉，在对话里呈现一个简短设计，然后停下。只有人类明确说"可以"之后才开始实现。不生成规格说明包。
- **架构级（Architectural）**——新项目、新子系统、会重组组件结构或改动他人依赖的接口的变更。走下面的完整流程。

拿不准时，选更重的那条路。任务中途发现的隐藏复杂度会把路径升级——停下来说明，然后升级；绝不中途降级。

反模式："太简单了，不用批准吧。"设计可以是对话里的两句话，但必须呈现并获得批准。随简单度缩放的是产出物的大小，绝不是批准这道闸门。

## 第 2 步 — 探索上下文

- 如果存在 PROJECT_STATE.md、ARCHITECTURE.md 等文档，先阅读。
- 检查相关代码。
- 范围检查：如果这个想法包含多个独立子系统，立刻指出来，并帮用户拆解成子项目。先头脑风暴第一个子项目；每个子项目各自走一遍规格 → 计划 → 实现循环。

## 第 3 步 — 一次一个问题地提问

规则：

- 每条消息只问一个问题。绝不要一口气抛出一堆问题。
- 尽量给选择题（A/B/C/D），并留"其他"作为出口；合适时也可以开放式提问。
- 想法已经清楚就提前收手。多数项目问 5-8 个问题足够。
- 如果用户说"你定"：选一个合理的默认值，明确说出来，并在简报里标注 `[AI-DECIDED]`（AI 代决）。
- 如果用户说"别问了"：用默认值填简报，并把每一条假设都记为待定问题（Open Question）。

按顺序覆盖（已经知道的就跳过）：

1. 问题与目标——痛点是什么，想要什么结果
2. 用户——他们是谁，怎么用
3. 成功标准——什么样子算"做完且有用"
4. MVP 范围——必须有什么，明确不做什么
5. 约束——技术栈、集成、期限、团队、平台、合规
6. 风险与未知——数据、规模、边界情况
7. UI 重的项目——风格参照（用户喜欢/讨厌哪些产品的外观）、桌面优先还是移动优先、信息密度（仪表盘式高密度还是留白式）、品牌约束（既有配色与字体）

## 视觉问题用 mockup

有些问题看图比看字清楚：两种布局二选一、页面骨架怎么分、信息密度合不合适、视觉风格选哪种。

不要一上来就主动提出做 mockup。当第一个真正的视觉问题出现时，单独发一条消息提出：

> "这个问题看图更好判断——我可以给每个选项做一个快速 HTML mockup，在你的浏览器里打开对比。要做吗？"

如果用户同意：

- 每个选项写一个自包含的 HTML 文件（内联 CSS、无需构建），放在项目的 `mockups/` 目录下，然后在浏览器里打开或把路径交给用户。
- 使用真实内容而不是占位乱文；选项之间的差异要正好落在要决策的地方。
- 问用户选哪个、为什么。把选择和被否掉的备选记进简报的"决策"表。
- Mockup 是用完即弃的设计探针，不是产品代码。它们为 UI_SPEC.md 和 DESIGN_SYSTEM.md 提供输入。硬性闸门仍然有效：设计获批之前不写应用代码。

如果用户拒绝，继续用文字推进，除非用户再提起，否则不要再次提出。

即使用户同意了，也要逐题判断：视觉问题（布局、外观、密度）用 mockup；概念问题（范围、需求、权衡）留在文字里。

## 第 4 步 — 提出 2-3 个候选方案

- 每个方案给出：一句话概括、优点、缺点、成本/风险。
- 把你的推荐放在最前面，并说明推荐理由。
- 狠狠执行 YAGNI：把每个方案砍到只剩 MVP 需要的东西。
- 由人类拍板选方案——或者认可你的推荐。

## 第 5 步 — 分节呈现设计

分成小节呈现；每讲完一节就问"到这里符合你的意图吗？"，确认后再继续：

1. 摘要——问题、用户、MVP
2. 方案与关键决策——包括被否掉的备选方案及其原因
3. 范围边界——做什么 / 不做什么
4. 风险与待定问题

UI 重的设计加第五节：关键页面的页面骨架（线框）。

用户要求就修改。用户没有确认的小节，不要往前走。

## 第 6 步 — 落成文字

- 套用 `templates/PROJECT_BRIEF.md` 填出 `PROJECT_BRIEF.md`：问题、用户、流程、MVP、约束、决策、成功标准、待定问题。
- 把选定的方案和被否掉的备选方案记进简报的"决策"表。`workflows/SPEC_GENERATION.md` 之后会把它们提升进 ARCHITECTURE.md。
- 每一条 `[AI-DECIDED]` 的默认值都要显式标注。
- 自查简报：还有占位符吗？前后矛盾吗？有歧义吗？范围大到一份规格装不下吗？就地修掉。

## 第 7 步 — 批准闸门

把简报交给人类，然后停下：

> PROJECT_BRIEF.md 已就绪。请过目——你批准后，我就开始生成规格说明包。

只有获得明确批准后，才进入 `workflows/SPEC_GENERATION.md`。
