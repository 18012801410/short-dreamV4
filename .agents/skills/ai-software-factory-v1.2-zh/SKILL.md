# AI 软件工厂（AI Software Factory）v1.2 中文版

## 使命

把 AI 编程从"一口气生成整个项目"改造成受控的工程流程：

产品想法
→ 头脑风暴
→ 需求
→ 架构
→ 领域模型
→ 契约
→ 开发计划
→ 小任务
→ 实现
→ 验证
→ 评审
→ 项目状态更新

人类负责产品方向和重大架构决策。
编码智能体在已批准的边界内负责实现。

## 文件地图

- `workflows/BRAINSTORM.md` —— 与用户逐题对齐意图并获得批准，视觉问题用 HTML mockup 对比（新项目/架构级改动先跑这个）
- `workflows/SPEC_GENERATION.md` —— 把想法变成规格说明包
- `workflows/NEW_PROJECT.md` / `NEW_FEATURE.md` / `BUG_FIX.md` / `REFACTOR.md` / `RELEASE.md` —— 各运行模式
- `checklists/SPECIFICATION_CHECK.md` / `ARCHITECTURE_CHECK.md` / `CODING_CHECK.md` / `RELEASE_CHECK.md` —— 各阶段质量门
- `templates/` —— 所有项目文档的骨架模板

# 1. 强制的项目文件

对每个非琐碎项目，创建一套"规格说明包"（Project Specification Pack）：

- PROJECT_BRIEF.md（项目简报）
- REQUIREMENTS.md（需求）
- ARCHITECTURE.md（架构）
- DOMAIN_MODEL.md（领域模型）
- TECH_SPEC.md（技术规格）
- API_SPEC.md（API 契约）
- UI_SPEC.md（UI 规格）
- DESIGN_SYSTEM.md（设计系统，UI 项目）
- AI_SPEC.md（AI 规格）
- AI_RULES.md（AI 规则）
- DEVELOPMENT_PLAN.md（开发计划）
- PROJECT_STATE.md（项目状态）

每个实现任务使用 TASK.md。

规格说明包是实现的唯一事实来源。
代码应该实现已批准的规格，而不是悄悄重新定义它。

流程规模要与改动规模匹配：单文件修复只需要一个 TASK.md；小的有界功能需要 TASK.md 加一次 PROJECT_STATE.md 更新；新项目或新子系统才需要完整的规格说明包。

在大量编码之前，先运行规格生成工作流（`workflows/SPEC_GENERATION.md`）和规格一致性检查清单（`checklists/SPECIFICATION_CHECK.md`）。

---

# 2. 规格生成

拿到新的产品想法时，不要立刻写代码。

如果这个想法还没有与人类讨论过，先运行头脑风暴工作流（`workflows/BRAINSTORM.md`）：对请求分类、一次一个问题地向用户提问、提出多个候选方案，拿到批准的 PROJECT_BRIEF.md。之后再生成规格包的其余部分。

先把想法转换成规格说明包：

产品想法
→ 头脑风暴
→ 产品简报
→ 需求
→ 架构
→ 领域模型
→ 技术规格
→ API 契约
→ UI 规格
→ 设计系统
→ AI 规格
→ 开发计划
→ 任务

对产品范围或架构有实质影响的模糊点，必须以"待定问题（Open Questions）"的形式记录，或提交给人类决策。

不要凭空捏造重要需求。

在实现之前，检查各规格文档内部是否一致。

# 3. 运行模式

## 新项目

遵循：

1. 产品探索
2. 需求
3. 架构
4. 领域建模
5. 技术契约
6. 开发计划
7. 项目脚手架
8. 基础实现
9. 功能实现
10. 验证
11. 发布

在架构和领域边界足够清晰之前，不要开始大规模编码。

## 新功能

先分类（见 `workflows/BRAINSTORM.md`）：有界改动走下面的步骤；架构级改动先运行头脑风暴工作流。

1. 阅读项目状态
2. 阅读架构/领域规则
3. 检查受影响的代码
4. 定义最小的连贯任务
5. 识别架构影响
6. 实现
7. 验证
8. 更新项目状态

## 缺陷修复

遵循：

1. 复现
2. 定位根因
3. 定义回归预期
4. 实现最小的安全修复
5. 新增/更新回归测试
6. 验证
7. 必要时更新项目状态

## 重构

重构之前：

- 说明原因
- 定义目标架构
- 识别受影响模块
- 识别必须保持不变的行为
- 评估迁移风险

不要把无关的功能改动混进重构。

---

# 4. 架构先行

在实现之前，明确定义：

- 系统边界
- 主要模块
- 归属（ownership）
- 数据流
- 外部依赖
- 提供方边界（provider boundaries）
- 重要不变量
- 特定技术栈的关注点

在可行的情况下，保持领域逻辑独立于 UI 和厂商 API。

对外部提供方使用适配器。

---

# 5. 领域先行

在设计 UI 或数据库表之前，先识别核心实体。

对每个重要实体定义：

- 标识（identity）
- 用途
- 字段
- 关系
- 生命周期
- 状态
- 不变量
- 归属
- 版本化要求

区分：

定义（Definition）
实例（Instance）
配置（Configuration）
执行（Execution）
结果/资产（Result/Asset）

不要把领域实体不必要地耦合到：

- React/Vue 等 UI 框架
- ORM 模型
- 厂商 SDK
- 画布库
- HTTP 载荷

---

# 6. 契约先行

在重要边界上定义显式契约：

- API
- 领域接口
- 命令
- 事件
- 提供方适配器
- 结构化 AI 输出
- 插件/节点接口

契约必须把输入、输出、校验、失败和归属说清楚。

---

# 7. AI 智能体协议

每个编码任务遵循：

阅读 → 检查 → 计划 → 实现 → 验证 → 报告 → 更新状态

写代码之前，智能体必须阅读相关项目文档并检查现有模式。

智能体不得悄悄重新设计架构。

如果需求与架构冲突：

停下（STOP）并报告：
1. 冲突
2. 原因
3. 受影响模块
4. 备选方案
5. 建议
6. 迁移成本

重大架构变更必须等待批准。

---

# 8. 任务边界

一个任务必须有：

- 一个主要目标
- 明确的范围
- 明确的非目标
- 验收标准
- 验证命令/检查项

优先选择可以独立评审的任务。

坏：
"把整个应用做出来。"

好：
"实现工作流图校验。不要修改 UI、持久化或执行层。"

---

# 9. 最小改动原则

优先：

小改动 > 大重构
复用 > 重复造轮子
现有模式 > 新抽象
显式行为 > 魔法
局部修复 > 无关清理

在功能任务中不要顺手清理无关代码，除非用户要求。

---

# 10. UI / 领域 / 基础设施分离

UI 层：
- 呈现
- 交互
- 视图状态
- 即时反馈

应用层：
- 用例
- 编排
- 命令
- 权限

领域层：
- 业务规则
- 实体
- 状态迁移
- 不变量

基础设施层：
- 数据库
- 外部 API
- 存储
- 队列
- 提供方 SDK

关键业务逻辑不得只存在于 UI 组件里。

---

# 11. 外部提供方

采用：

应用层
→ 提供方接口
→ 提供方适配器
→ 外部服务

绝不允许：

UI 层
→ 外部服务

提供方特有的细节止步于适配器边界。

---

# 12. AI 作为受控操作者

当 AI 修改结构化的应用状态时，优先采用：

用户意图
→ AI 计划
→ 结构化命令
→ 校验
→ 应用
→ 结果

命令应当显式、可审计、经过校验。

AI 不得直接修改任意内部状态。

---

# 13. 状态机

对重要的生命周期状态显式建模。

定义：

- 状态
- 合法迁移
- 非法迁移
- 迁移副作用
- 重试/取消行为

避免散落的状态字符串和隐藏迁移。

---

# 14. 版本化

如果用户或 AI 反复修改某个重要工件，考虑引入不可变版本。

当可复现性重要时，执行记录应引用它实际执行的精确版本。

版本化改进：

- 回滚
- 调试
- 可复现性
- 审计
- AI 迭代

---

# 15. 验证

代码能编译不代表任务完成。

在适用的情况下验证：

- 类型检查
- Lint
- 单元测试
- 集成测试
- 构建
- 端到端测试
- 手动行为验证
- 错误状态
- 加载/异步状态
- 回归

不要为了让构建通过而删除或削弱测试。

---

# 16. 完成的定义

只有满足以下条件，任务才算完成：

- 实现满足需求
- 验收标准通过
- 测试通过
- 必需检查通过
- 错误已处理
- 没有引入无关回归
- 文档/状态已更新
- 架构影响已报告

---

# 17. 项目状态

每个有意义的里程碑之后，更新 PROJECT_STATE.md。

它必须记录：

- 当前阶段
- 当前任务
- 已完成工作
- 生效中的决策
- 已知问题
- 阻塞项
- 下一个任务

这让新的智能体/会话能快速恢复上下文。

---

# 18. 人类与 AI 的职责分工

人类：
- 产品方向
- 优先级
- 领域语义
- 重大架构
- 安全决策
- 技术战略
- 验收标准

AI：
- 实现
- 测试
- 调试
- 局部重构
- 文档
- 代码探索
- 重复性工程

AI 是实现能力的放大器，不是产品负责人。

---

# 19. 黄金法则

不要问：

"能不能把这个做出来？"

要问：

"什么是最小的、经过验证的改动，能让已批准的架构朝这个目标前进一步？"

然后重复：

计划。
实现。
验证。
评审。
更新状态。
继续。
