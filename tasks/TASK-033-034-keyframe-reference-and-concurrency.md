# TASK-033 / TASK-034：关键帧参考图隔离 + 并发 Worker 提速

日期：2026-09-16
来源：用户反馈两张关键帧「人物反正坐、又坐到驾驶员位置」以及「生图效率太低了，超级慢」。

## TASK-033 关键帧参考图隔离（补人 + 特征串味的根治）

### 诊断（实测取证）

对「末班车复仇」新批次关键帧逐张目检 + 放大取证，发现两类缺陷：

1. **画面里多出人**：S01G04 只有一名乘客坐着打电话的构图里，背景多出一个人影。
2. **身份特征串味**：同一张图里坐着的乘客腰上挂着**另一个角色的旧工牌**（黄色挂绳），
   而该道具属于司机陈默。

**根因**：关键帧走 Qwen-Image-Edit 图生图通道，每一段都固定传 3 张参考图——
`_segment_reference_cards` 按"角色优先、其次场景、最后道具"取满 3 张，于是
车上双人段 = 两张角色卡 + 场景卡。图生图模型的行为是**给谁的脸就把谁摆进画面**：

- 第二张角色卡即使不在这一镜构图里，也会被摆进来（或在背景补一个人影）；
- 两张卡同时进入，特征互相污染（道具挂到别人身上）。

提示词本身一直是对的（逐人写了座位与朝向）。**文字与参考图冲突时，图生图模型听图的。**

### 修复

| 层 | 内容 |
|---|---|
| 领域 | `SubjectPlacement.in_frame: bool = True`——该角色在本段第 0 帧画面里是否可见（可见含背身/侧身主体；画面外/被遮挡/仅远处剪影为 false）；存量分镜无字段默认 True |
| 分镜 Agent | schema 增 `in_frame` 说明；`C6` 规则要求逐人标注——只有开场帧确实出现的人才填 true，否则关键帧会把不该出现的人画进画面 |
| 图生图通道 | `_segment_reference_cards` 只传**画面内可见**角色的卡（≤2）+ 场景卡；**道具卡不再传**（白底产品图对场景静帧没有身份价值，只带来白底/物件漂移）。存量无 `in_frame` 时保持旧行为 |
| 关键帧提示词 | 画面人名单只列 in_frame 角色，并**锁死人数**："the frame contains exactly N people, each appearing exactly once"；本段在场但画面外的角色用正向状态句说明（"X stays outside the frame, and the rest of the visible space is empty of people"）；全员画面外时直接声明画面无人 |

### 验证

- 单测：`test_h3_compiler.py` 增画面外角色排除 / 全员画面外两例；`test_frame_stage.py`
  增参考卡裁剪（只留 in_frame 角色 + 场景）与存量回退两例。
- 线上验证：修复后重出此前最差的 S01G04——**司机在驾驶座握方向盘、乘客坐在乘客位，
  画面恰好两人，无多余人影、无道具串味**；随后 13 张按新逻辑批量重出。

## TASK-034 并发 Worker（生图/生视频吞吐）

### 诊断（数据）

对关键帧任务逐条统计等待与执行时间：

```
job 等待(串行排队)  执行(平台侧)
1      2s          246s
2    248s          215s     ← 等待 = 前一个任务的全长
3    463s          210s
4    673s          209s
...
```

结论：**单张图平台侧固定要 200s 左右，而"等待"完全是我们自己一次只跑一件事造成的**。
worker 引擎的 `run_once` 同步阻塞执行 handler（图片/视频都是），整批时间 = N × 单件时间。

代码里其实早已埋好并发基础：任务认领是条件 UPDATE 抢占（`claim_next_runnable`），
多进程只有一个能把 pending 置为 running；`EngineConfig.queue_full_retry_delay_sec`
也已处理平台并发额度占满的拒绝。

### 修复

| 项 | 内容 |
|---|---|
| 额度占满不烧预算 | `_schedule_retry`：`TASK_QUEUE_MAXED` 失败不再消耗重试预算（同步放宽 max_attempts）——额度占满是并发提交的常态，扣预算会把整批任务打成"重试用尽"全灭（2026-09-16 实测 13 张资产图全灭） |
| 启动恢复隔离 | `python -m server.worker --no-recover`（池成员）/ `--recover-only`（池启动前跑一次）。**原因**：`recover_stale_running` 把所有遗留 running 任务判为中断，多进程各自启动会互相打断在途任务——实测新起一个 Worker 就把在线跑图任务判成 INTERRUPTED 并重排，白费一张图 |
| 推进安全门 | `running_video_jobs()` 过滤 `provider_task_id != ""`：并发池下若把"别的进程正在阻塞执行"的视频任务也返回，另一个进程会拿它重跑一遍 handler = 重复生成整段视频（双倍消耗） |
| SQLite 并发 | 连接建立时 `PRAGMA busy_timeout=30000`（WAL 已开）：并发写冲突时等待重试而非立刻报 locked |
| 运维入口 | `scripts/run_workers.py --count 3`（池外先跑一次恢复，再以 `--no-recover` 起成员）；`--status` / `--stop` |

### 验证

- 单测：`test_task_queue.py` 增「队列满不消耗重试预算」（连跑 4 轮超过 max_attempts 仍可重试）。
- 线上：3 Worker 池下**同时有 2 个关键帧任务在跑**（DB 证据），未见 TASK_QUEUE_MAXED 拒绝
  ——即 RunningHub 账号并发额度 ≥2；单张 200s 从"累加"变为"并行"。

## 遗留与后续

- 关键帧分辨率 1080×1920 而最终成片是 480×864（9:16），像素上过度指定约 5.6 倍；
  降分辨率或降采样步数（现 20 步 cfg 4）可进一步压缩单张 GPU 时间，但需在 RunningHub
  改工作流并重新发布，属用户侧操作，待拍板。
- 图片/视频 handler 目前仍是"一次性阻塞"模型；引擎里 `_advance_running_videos` 的两阶段
  （提交→跨轮询）路径已就位但未启用。改为真正的提交/轮询两阶段后可支持单进程内并发 +
  按账号额度精细限流，比多进程更可控（需要 ownership 标记）。

## TASK-036 关键帧提示词改画面描述式

用户指出提示词读起来像视频提示词（锁定指令清单）而非画面描述。原提示词确实把 H3 视频
那套锁照搬了：元指令（`each appearing exactly once`、`appearance and identity must match
exactly`）+ 大段中文身份串 + **两条互相打架的 `setting:`**（把本段所有场景资产都写进去了）。

`{风格} Cinematic still frame: {分镜产出的画面描述} , {N people in frame - 谁在画面哪里} ,

画面外角色写成 `X is off camera, the rest of the space is empty`；走图生图通道（有角色卡锁脸）

# TASK-037：对齐豆包 frame.md 的关键帧写法（I2I 编辑指令）

日期：2026-09-16
来源：用户指出"还是不理想"，并给出豆包 skill 的 `references/frame.md` 作为参照。

## 豆包做法的关键差异

| 维度 | 我们原来 | 豆包 frame.md |
|---|---|---|
| 提示词性质 | 一段画面陈述（面向文生图） | **I2I 编辑指令**：正文显式引用 `[img0]/[img1]…`，逐张声明"保留什么/改什么" |
| 图与文的关系 | 图是隐形输入，正文不提 | 每张图都要说明用途与保留内容（脸型/服装结构/空间透视/光态） |
| 描述顺序 | 人物清单式 | **空间线性**：背景 → 主体 → 局部 → 道具 |
| 方向性物体 | 未强调 | 方向公式：人物朝向+视线+物体朝向+手部接触+可见面+距离 |
| 风格与画幅 | 风格行无约束、无画幅 | 首句风格词与剧本头一字不差；结尾必须写画幅比例 |
| 关键帧数量 | 每段固定 1 张 | 按"命中判定标准"动态 1–N 张，禁止套首中尾模板 |

## 一次失败的尝试（重要教训）

按豆包格式重写后（逐图"保留…不变"+ 空间线性 + 画幅），S01G01 反而更差：
**司机坐到乘客位、驾驶座空着，画面还多出一个戴口罩的人**。

根因：场景卡是"空无一人"的空镜驾驶座。指令里写"保留 [img2]（驾驶座）的空间结构、
透视与光态不变"，等于要求模型**别动那个空座位**——人只能被挤到过道和别的座位上。
（与 TASK-036 发现的"空镜卡偏置"是同一个机制，被"保持不变"锁放大了。）

## 最终定稿

保留经过验证的画面描述主干，只吸收豆包真正有价值的部分：

1. **逐图身份绑定只给角色**：`保持这些人物的身份不变：[img0]（陈默）的脸部特征、发型与服装结构（深蓝色旧夹克，灰色T恤）…`
2. **场景卡只声明"以哪张为准"**，不给"不变"锁：`background: …, 以 [img2]（末班公交车驾驶座）为准`
3. **空间线性顺序**：`Cinematic still frame: {画面描述} → background: → N people in frame → visible props:`
4. 结尾画幅（`9:16 画幅`）+ 画质词；风格行仍取项目 style。

实测（S01G01 第 8 版）：**司机正确在驾驶座、双手握方向盘、恰两人、无多余人影**。
遗留：被遮挡的次要角色服装仍可能漂移（周明远渲染成灰毛衣+眼镜，未完全贴合参考卡）。

## 未采纳项（待用户拍板）

- 豆包的**关键帧数量策略**（按命中标准 1–N 张）：我们视频阶段把每段开场帧当 `<Picture 1>`，
  改数量涉及流水线契约，改动大。
- 豆包的**构图细则**（9:16 人脸/上半身安全区、关键道具中下部、双人左右关系、180° 轴线）
  与**方向性物体公式**：可直接并入关键帧提示词，属下一步收益明确的小改动。

## 验证

后端 200 项全绿；S01G01 用新指令重抽并通过目检（司机在驾驶座）。

# TASK-038：关键帧链式锚定（实测否决）

日期：2026-09-16
来源：用户问"场景不传，能保证场景不漂移吗"。

## 问题定位（不花钱的证据）

同场景各段的关键帧**在传了场景卡的情况下依然在重造空间**：
S02G01 是粗黄色扶手立柱＋蓝座椅，S02G02 变成灰色金属扶手＋红色 LED；S01G01 顶灯是长灯带，
S01G04 变成圆形小灯。说明空镜场景卡对空间的约束力很弱（图生图模型拿"两张角色卡 +
一张空镜 + 一段文字"整体重画），而"空"还会把人挤走（TASK-037 已证）。

结论：场景一致性**不能靠场景卡保证**，需要别的锚。

## 尝试的方案与实测结果

方案：同场景紧邻前段有已批准关键帧时，把它作为参考图送进图生图（链式锚定），
非链头不再传空镜场景卡。

两次实测（S01G02 应为"后视镜特写"）：

| 变体 | 结果 |
|---|---|
| 链锚点作 [img0]（底图） | 车内一致 ✓，但**构图被锁死**：画成与上一段几乎相同的侧拍司机 ✗ |
| 链锚点放末位（仅作空间参考） | 仍然锁构图 ✗（只是顶灯亮了） |

**否决**：在这个图生图模型上，只要把上一帧放进参考图，它的构图就会压过本帧的文字要求，
无论放第几位。关键帧的职责是"给每段不同的开场画面"，锁死镜头等于毁掉剪辑节奏。

## 最终处置

- 代码：不实现链式锚定，参考图固定 = 画面内角色卡（≤2） + 场景卡；
  加回归测试 `test_reference_cards_do_not_chain_previous_frame` 防止以后又加回来。
- 场景一致性改由既有机制承担：**视频阶段**（H3 每段都带场景卡，且把本段关键帧作
  `<Picture 1>`）＋**连续段尾帧接力**。关键帧阶段接受"同场景各段的空间细节不完全一致"。
- 记录在 `_segment_reference_cards` docstring，说明为什么不做。

## 构图细则 + 方向性物体（豆包 frame.md 余下部分）

并入 `compile_keyframe_prompt`（纯提示词改进，零生成成本，存量分镜在下一次生成时自动生效）：

- **按画幅的构图细则** `_composition_line(aspect)`：竖屏（9:16/3:4/2:3/4:5）——人脸与上半身
  落在安全区、关键道具放中部或下三分之一、双人同框保持左右关系、重要元素不贴边；
  横屏——三分法、视线前方留呼吸空间、前景/中景/远景纵深、对话或对峙保持 180° 轴线。

  手机/镜子/后视镜/车门/画纸/工牌/现金等，命中则追加"必须方向自洽：人物朝向、视线方向、
  物体朝向、手部如何接触、观众能看到物体的哪一面、物体与人物距离"。标签只输出**物体名**
  （道具资产名优先，如"一沓现金"），不截句子——首版截断出"Close-up of""holding his"
  这类噪声已修。

实测文案（S02G04 / S01G02）：`方向性物体（一沓现金、智能手机）…` / `方向性物体（mirror）…`；

# TASK-040：视频提示词可手改（人工覆盖）+ 展示即生产文本

日期：2026-09-16
来源：用户问"这块是视频提示词吗"，发现分镜 Tab 里那个可编辑的提示词框在生产时会被实时重编译覆盖（TASK-032 的副作用），页面没有人工覆盖入口。

## 改动

| 层 | 内容 |
|---|---|
| 领域 | `H3Prompt.manual_override: bool`——正文被人工改过即置 True |
| 用例 | `cmd_edit_segment`：正文与改前不同 → 置 `manual_override=True`（除非显式传 `prompt_manual_override=false`）；`reset_prompt=true` 时服务端按当前结构化数据重编译并清除标记；`_compile_production_prompt` 遇到 `manual_override` 直接返回存储文本（保留 7000 字符闸门） |
| 接口 | `storyboard_dto` 透传新字段（`model_dump` 自动带上）；分镜接口补 `prompt_view: compiled/manual` |
| 前端 | 分镜 Tab 每段：`实时编译` 标识（显示的就是将送给 H3 的那一份）/ `人工覆盖（生成时不再重编译）` 徽标 + 「恢复自动编译」按钮 + 编辑提示语 |

## 顺带修掉两个真问题

1. **`cmd_edit_segment` 嵌套 dict 未建模**：旧实现只把 `h3_prompt`/`shots` 转成实体，`asset_refs` 等仍是 dict，`validate_segment` 直接 `AttributeError: 'dict' object has no attribute 'asset_id'`——页面「保存段修改」会踩。现改为按 `Segment` 字段白名单过滤 UI 只读字段（`references`/`resolution_status`）后整段 `model_validate`。
2. **页面显示旧缓存造成假告警**：`segment_reference_previews` 用存储文本核对 `<Picture>` 编号，而关键帧批准后生产会带 Picture 1 槽位重编译 → 误报「⚠ 编号错位」（实测 S01G01：6 张参考图 vs 文本只提 1–5）。现预览与展示都用**生产实际会送出的文本**（未人工覆盖则实时编译），同一处修掉假告警与"看到的不是将发出的"。

## 验证

- 后端 204 项全绿（新增人工覆盖→生产直用→恢复自动的闭环用例）；前端 16 项全绿 + `tsc -b`。
- 浏览器实测：分镜 Tab 出现「实时编译」标识、人工覆盖徽标与「恢复自动编译」按钮；S01G01 假「编号错位」告警消失（现为 6 张对 1–6，一致），字符数 3839/7000。

## 使用方式

分镜 Tab 展开某段 → 直接改正文 → 「保存段修改」即视为人工覆盖（生成时以你的版本为准）；
想交回编译器点「恢复自动编译」。注意编辑会新建草稿版本（原 active 转 superseded），
需重新确认分镜才生效——这是既有确认门行为，不是本次改动引入。

# TASK-041：镜头内容改中文展示（英文原文折叠）

日期：2026-09-16
来源：用户指着关键帧页那段英文镜头描述："镜头的这个还是改成中文吧"。

## 做法：展示层用中文，生成层不动

镜头动作（`shots[].action`）是英文的**生成素材**——它逐字进 H3 英文正文，改语言要连带改视频提示词（风险未实测）。但页面上给人读的内容完全可以用中文：
每镜都记着它认领了剧本里的哪些节拍（`shot.beat_refs`），而**剧本节拍本身就是中文**（写剧本时的画面描述，用户已确认过）。所以：

- 服务端：`WorkbenchService.shot_beats_zh(pid, segments)` 把每段每镜认领的节拍原文（含 `音效/画面文字/转场` 前缀与台词 `说话人：台词（语气）`）解析出来；
  `/frames` 与 `/storyboard` 两个接口都返回 `shot_beats_zh`。
- 前端：关键帧页与分镜页的每镜展示改为**中文节拍**（多条用「；」连接）；英文动作段收进 `英文原文（送视频提示词的动作段）` 折叠项，默认不展开；
  节拍缺失（旧分镜没认领）时回退显示英文原文。

## 验证

- 后端 204 项、前端 16 项 + `tsc -b` 全过；ruff 全过。
- 浏览器实测两页：`陈默穿着旧夹克坐在驾驶座，车载时钟显示01:47，后视镜里映出最后一排闭眼打盹的西装男。；音效公交车引擎低沉的轰鸣声` 直接可见；英文整段默认折叠。
- 顺带确认节拍认领覆盖完整（S1 场景 8 拍被 4 段全覆盖；个别拍由两个镜头共同承担属正常，说明该拍画面在镜内延续）。

## 边界

提示词层（视频与关键帧）**仍是英文**：H3 六段结构字段官方要求英文，关键帧指令与 Qwen-Edit 的搭配也以英文描述 + 中文身份/场景锚点为主。
若要把提示词正文整体改中文，属于另一件事：需实现 `prompt_lang=zh`（当前该分支为空实现）、重新生成分镜，并实测中文正文下的视频质量。

## TASK-041 补丁：同拍镜头不重复播节拍

用户看到镜1/镜2 显示同一条中文节拍，问"这两个镜头怎么内容是一样的"。
实际是两个镜头**认领了同一拍**（S01G01：镜1→[1,7]、镜2→[1]，即同一时刻用全景+特写两个景别覆盖），
内容并不相同（英文动作段一张是"全景建立"、一张是"切特写仪表盘"）——是我这次中文展示把同一条节拍
播了两遍，读起来像重复。

修法（`client/src/lib/format.ts: dedupeShotBeats`）：本镜认领的节拍若**没有新增**（被上一镜全部覆盖，
含完全相等与子集两种情形），则不再重复节拍原文，改显示
`（与上一镜同属一拍，景别：close-up, static）`。关键帧页与分镜页共用该函数。

实测：S01G01 镜2 → `（与上一镜同属一拍，景别：close-up, static）`；
S01G02 镜2 → `（与上一镜同属一拍，景别：extreme close-up, static）`；镜1 仍显示完整中文节拍。
